# Agent Note: 单仓交付与固定后端

Status: implemented

## 问题

早期方案让 MirrorOPD 提供算法、MD-OPD 提供后端与编排，依赖相邻源码、父目录环境和人工同步。搬到第二仓库会再次接线已有缓存、梯度参照、归约、同步及评测，使一次实验的执行来源难以独立确认。

## 决策

MirrorOPD 负责第一方算法、输入校验、判分、运行编排和审计，分布式训练继续复用固定 verl 后端。以实际源码字节及输入身份记录执行版本，交付边界见[架构](../../../../docs/架构.md)，验证证据见[版本说明](../../../../docs/2026-10-15-MirrorOPD全面重构说明.md)。

任务配置、原生参数、执行身份和参数矩阵的后续决策见[verl 实验配置与运行管理](2026-10-15-verl实验配置与运行管理.md)，不改变本记录的单仓和固定后端边界。

## 考虑过的替代方案

双仓交付方案将 backend 与编排放进 MD-OPD。2026-10-12 单仓决策保留已有 MirrorOPD 生产链路作为起点，理由是复用已验证的缓存、损失、CPU oracle、归约与真实 outer/inner 接线，先检验行为再扩展能力。

旧提案还建议 vendored 源码树；当前交付使用 manifest 加固定补丁，未实现该建议。现有材料没有记录两种方式的完整取舍依据，不能把未实施建议补写成经过验证的拒绝结论。

## 后果

新机器仍需获取固定后端和软件依赖、模型及数据；一次普通 checkout 并不包含全部上游源码。后端升级必须核对实际基线与全部补丁，执行合同测试和 GPU 验证。增加第二个生产后端前，现有单后端事实不足以证明通用插件接口的需要。

输出层分块、冻结缓存布局和显式内存预算的补充决定见[冻结缓存与分块输出层](2026-10-15-冻结缓存与分块输出层.md)。
