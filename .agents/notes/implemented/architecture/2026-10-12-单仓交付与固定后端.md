# Agent Note: 单仓交付与固定后端

Status: implemented

## 问题

旧生产入口把数学判分、数据路径和训练启动绑定到邻接 MD-OPD、父目录 `.bashrc` 及多套实验 launcher。将已有纯张量内核、数学参照、缓存、更新与评测链路整体迁往另一产品仓库，需要再次接线并核对已有证据。原讨论见[单仓历史提案](../../../../docs/operations/2026-10-15-单仓与算法抽象历史提案.md)。

单个后端承载 Ray、FSDP、vLLM 和必要控制流修改，第一方生产公式又需要独立于框架验证。交付边界必须同时说明算法归属、后端版本和外部依赖，避免把忽略目录里的未提交修改当作可复现产品。

## 决策

MirrorOPD 是第一方产品入口。当前包维护纯张量 `core/`、共享 `runtime/`、独立 `scoring/`、可组合 profiles 和薄 `integrations/verl/`；公开运行器消费显式模型与数据路径，不依赖邻仓源码或 shell 函数。现有三算法、配置与生命周期见[架构说明](../../../../docs/架构.md)。

生产后端以 [backend.json](../../../../src/mirroropd/integrations/verl/backend.json) 的固定基线加[完整补丁](../../../../src/mirroropd/integrations/verl/backend.patch)交付，通过准备命令获取实际源码。启动前 [verify_backend](../../../../src/mirroropd/runtime/provenance.py) 核对 HEAD、完整 binary diff 与运行目录中未版本化的源码，随后冻结实际执行字节。忽略目录本身不是版本事实源。

后端继续承担分布式和模型执行，第一方公式在可独立验证的内核维护。当前只有一个生产后端，没有通用 backend 插件系统。库依赖、GPU 软件栈、模型权重和数据分别准备；普通主仓 checkout 不包含完整后端源码，也不意味着这些外部资源已经可用。

本记录维护已实施的单仓职责与固定后端边界。历史提案要求的“单 checkout 包含后端完整源码”未达到，通用 capability planner、更多生产算法及全部数据下载路线也未作为当前接口交付。它们保留在原提案中，不自动登记为正在实施的功能。

## 考虑过的替代方案

1. 让 MD-OPD 承载后端与编排，MirrorOPD 作为算法组件。原[双仓接入方案](../../../../docs/operations/2026-10-10-OPD统一抽象与MD-OPD接入方案.md)讨论过此边界。单仓提案指出，切换产品仓会重新接线已有 cache/loss、CPU oracle、outer-inner、评测与证据。当前第一方职责留在 MirrorOPD，其他项目保留来源与研究参照价值。
2. 将固定后端完整源码以 subtree 或 vendored snapshot 纳入主仓。原提案希望减少大型手工补丁的审阅和升级成本，并让普通 checkout 直接含后端源码。当前固定基线加补丁提供精确重建与运行前核验，仍需要额外获取源码；这两种交付属性不能混为一谈。已有材料没有记录从整树入库建议转为继续使用补丁的完整评审理由，不能补写成整树方案已被性能或维护实验否决。
3. 采用 submodule 指针或动态后端插件。原提案指出 submodule 仍需额外获取源码；当前版本验证说明采用“出现第二个实际后端后再提取共同接口”的边界。现有实现不承诺任意 backend 可替换，也不把自动准备等同于完整离线交付。

## 后果

核心损失、缓存和配置测试可与分布式训练分开；第一方判分和输入处理不再通过邻仓导入。后端升级仍需重放全部补丁，核对布局、缓存运输、全局归约、版本、seed 与评测合同，再做真实 GPU 小规模验证。当前范围与已保存证据见[版本验证说明](../../../../docs/2026-10-15-MirrorOPD全面重构说明.md)。

固定基线与完整 diff 可以识别错误后端，却没有消除补丁审阅、升级冲突和外部源码获取的成本。模型、数据与运行身份仍须记录实际内容；同名目录、相同 commit 或准备命令成功不能替代完整运行审计。

若后续需要离线源码交付、采用第二个后端或改变后端归属，应另立决定并与本记录互链，比较实际交付和维护成本。既有后端内置建议的取舍理由仍有缺口；这不影响确认当前实现事实，但限制了对历史选型原因的解释。
