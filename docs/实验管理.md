# 实验配置与批量运行

MirrorOPD 使用严格 Job 管理单次实验，复用固定 verl 后端的训练、优化器和 checkpoint 实现。任务 profile 组合模型、数据、配方和评测；study 将参数组合展开成普通 Job，顺序调用已有运行器。选型依据和六仓调研见[实验管理决策](../.agents/notes/implemented/architecture/2026-10-15-verl实验配置与运行管理.md)。环境、模型、数据与固定后端的准备见[运行与复现](运行与复现.md)。

## 任务与显式覆盖

内置 `math-four-gpu` 任务选择同名配方、`deepseek-justrl` 模型、`dapo-math` 数据和 `math-r16` 评测；`math-smoke` 使用短生成配方和四题、每题两次的短评测。以下路径是占位值；`plan` 不读取输入或检查 GPU。

```bash
mirroropd plan --task math-smoke --algorithm on_policy \
  --var model_root=/models --var data_root=/data \
  --output runs/math-smoke-plan.json
```

配置顺序为任务中的 profile 引用、显式 `--recipe/--models/--dataset/--evaluation` 选择、变量展开、Job 默认值、`--set`，以及最终的 `--algorithm/--name/--wandb`。指定 `--algorithm on_policy` 强制每个 fresh batch 一次更新。未通过该选项而直接覆盖 `objective.algorithm` 时，仍须满足 Job 的 inner 约束。

模型、数据、配方、评测和任务都可使用内置名称或 JSON 文件。任务文件的相对引用以任务文件目录为基准；study 的显式 profile 引用以 study 文件目录为基准。变量只从显式 `--var` 读取。任务不是任意递归继承机制，未知字段和缺失变量在启动前失败。

```json
{
    "schema_version": 2,
    "recipe": "math-four-gpu",
    "models": "deepseek-justrl",
    "dataset": "dapo-math",
    "evaluation": "math-r16"
}
```

`--evaluation` 替换整个评测 profile 后补齐默认值，`--set evaluation.*` 再覆盖已知字段。当前一份 Job 的所有验证数据仍共享同一评测协议和 scorer；独立 profile 不代表已经增加逐数据集协议或最终 test 阶段。相同协议下各数据源的逐题记录和指标继续独立保存。

## 原生优化器与 checkpoint

新增参数由 `runtime/config.py` 校验，并由现有编译器映射到固定 verl；不开放绕过算法约束的任意 Hydra 覆盖。

| 字段                                                  | 行为                                                                               |
| ----------------------------------------------------- | ---------------------------------------------------------------------------------- |
| `training.learning_rate`、`weight_decay`、`clip_grad` | 继续管理学习率、权重衰减和梯度裁剪                                                 |
| `training.optim.optimizer`                            | `AdamW` 或 `Adam`，使用 `torch.optim`                                              |
| `training.optim.betas`、`eps`                         | Adam 系优化器参数                                                                  |
| `training.optim.lr_scheduler_type`                    | `constant` 或 `cosine`                                                             |
| `training.optim.lr_warmup_steps`                      | 正数表示 warmup outer 数；默认 -1 使用比例                                         |
| `training.optim.lr_warmup_steps_ratio`                | warmup 占总 outer 的比例，默认 0                                                   |
| `training.optim.min_lr_ratio`、`num_cycles`           | cosine 最小学习率比例与周期参数                                                    |
| `checkpoints.every`                                   | 每隔多少 outer 保存；0 关闭，启用时最后一轮也保存                                  |
| `checkpoints.max_to_keep`                             | 原生 actor checkpoint 最近保留数量，默认 2                                         |
| `checkpoints.save_contents`                           | `model`、`optimizer`、`extra`、`hf_model` 的非重复组合，须含 `model` 或 `hf_model` |

固定 worker 只在每个 outer 的最后一次 inner 更新后推进 scheduler；同一 outer 中所有 inner 使用相同学习率。warmup 和衰减的总步数是 outer 数，不能将 BPO 的 800 次优化更新当成 800 次调度。正数 warmup steps 与非零比例不能同时设置；原生 0 steps 仍回退到比例。

```bash
mirroropd plan --task math-four-gpu \
  --var model_root=/models --var data_root=/data \
  --set training.optim.lr_scheduler_type=cosine \
  --set training.optim.lr_warmup_steps_ratio=0.1 \
  --set checkpoints.every=5 --set checkpoints.max_to_keep=3 \
  --output runs/cosine-plan.json
```

checkpoint 位于运行目录下的 `checkpoints/global_step_<outer>/actor/`。`hf_model` 请求原生 HF 导出，不是完整训练状态；去掉 optimizer 或 extra 也不能获得完整恢复。自动 resume 继续关闭，当前没有 best checkpoint 选择或 W&B Artifact 上传协议。

## 运行身份与 W&B

每次执行在 `identity.json` 中保存独立的 32 位十六进制 `run_id`。显示名称由 Job 名称、算法、训练 seed 与执行短 ID 生成。`run_id` 同时用于本地事件、运行清单和 W&B ID；suite 的各算法不再共享显示名称或执行 ID。

`--name` 指定名称前缀，`--output` 指定输出位置。省略输出位置时，程序在当前目录的 `runs/` 下自动分配带执行短 ID 的新目录。显式目录可以有任意名称，但所有运行产物仍记录同一个执行身份；已存在目录会被拒绝。

W&B 的 project、entity、group、tags 和在线/离线开关仍由 `logging.wandb` 管理。未指定 group 时，普通运行使用 Job 名称，suite 子任务继承组目录的 group，study 使用研究批次名称。标签自动包含算法与训练 seed，并合并用户 tags。W&B config 同时保存 `mirroropd` 完整 Job 和 `run_identity`；`wandb.json` 记录 SDK 的执行身份和在线链接或离线模式。

```bash
mirroropd run --task math-smoke --algorithm on_policy \
  --var model_root=/models --var data_root=/data \
  --wandb offline --set logging.wandb.group=math-canary \
  --set 'logging.wandb.tags=["canary","math"]' \
  --backend upstream/TA-OPD-v2 --detach
```

终端输出控制进程身份和实际目录。`status`、`stop`、`audit` 继续接收该目录。每次重试创建新的执行 ID；复用 W&B ID 不作为恢复训练的入口。逐更新统计继续来自 worker 的全局归约记录，按 update、outer 和 evaluation 分别设置横轴。

## 参数矩阵

study 定义公共 profile 选择和离散参数网格。下面的两学习率、两 seed 产生四个 Job：

```json
{
    "schema_version": 2,
    "name": "math-smoke-grid",
    "base": {
        "task": "math-smoke",
        "algorithm": "on_policy"
    },
    "grid": {
        "training.learning_rate": [0.000001, 0.000002],
        "training.seed": [42, 43]
    }
}
```

`base` 支持 task、recipe、models、dataset、evaluation、algorithm、variables 和 overrides。网格的 `task/recipe/models/dataset/evaluation/algorithm` 轴选择 profile 或算法；其他轴通过同一个 Job 覆盖解析器设置已知字段。`--var` 覆盖 base 的变量，额外 `--set` 覆盖 base 的 overrides，但不允许遮盖网格轴。

所有组合先完整解析和校验。空轴、未知字段、非法类型、归一化后的重复 Job 或超出 `max_trials`（默认 256）都在启动前失败。没有隐式跳过非法组合。例如同时枚举 on-policy 与多个 inner 值可能归一化为重复配置，程序要求先修正研究设计。

```bash
mirroropd study plan --config smoke-grid \
  --var model_root=/models --var data_root=/data \
  --output runs/smoke-grid-plan.json

mirroropd study run --config smoke-grid \
  --var model_root=/models --var data_root=/data \
  --backend upstream/TA-OPD-v2 --output runs/smoke-grid-prepare \
  --prepare-only
```

准备检查不预约 GPU。真实训练使用另一个新目录并去掉 `--prepare-only`。内置 `math-lr` 是三学习率、三 seed 的完整 BPO 数学实验，不能把它当短任务启动。

每个 trial 的 key 从完整计划 Job 的 `config_id` 派生。study 保存 `study.json` 和 `summary.json`，每个 trial 位于自己的子目录并继续保存输入、源码、日志、逐题结果和审计。矩阵顺序执行，复用当前 GPU 预约；普通训练异常会记录失败并继续下一项，停止信号终止批次，不再启动后续任务。

```bash
mirroropd study status runs/my-study

mirroropd study retry runs/my-study \
  --backend upstream/TA-OPD-v2 --output runs/my-study-retry \
  --detach
```

重试要求原控制进程已结束，读取原批次冻结的 Job，不重新读取可能已经修改的 profile。它只跳过重新审计通过的 completed 项；prepared 项尚未训练，仍会进入重试。新目录保存 `retry_from`，原目录不覆盖。运行中的批次不能通过 retry 启动重复任务。

status 汇总状态、参数坐标、预算、执行身份、最终评测及 W&B 信息。completed 必须重新通过完整审计，否则显示 invalid 并可重试。计划阶段不读取输入，实际准备会归一化输入路径，因此汇总同时区分计划配置身份与执行配置身份。当前完整配置哈希包含名称、路径和日志配置，不能当作跨机器的科学条件指纹。

## 验证边界

参数计划报告 outer、实际优化次数、训练回答数、训练 response token 预算上界和评测轮数。上界不等于实际生成量或耗时。比较三算法时同时固定或记录 outer、inner、生成预算、评测协议及运行时间。

CPU 测试覆盖组合校验、原生配置与优化器、调度单位、身份、离线 W&B、失败隔离和停止/重试。GPU 软件栈、模型架构和显存容量仍需在空闲设备上运行 canary；既有历史 GPU 验证不自动覆盖新参数。outer 边界恢复需要额外持久化和中断恢复实验证据，当前保持未支持状态。
