# OPD 上游精度与梯度累积审计

## 已确认的代码错误

MirrorOPD 新增的`distillation_ppo_loss`分支在调用`distillation_loss`之后才调用`populate_global_batch_info`。而`distillation_loss`已经把 token 级 surrogate 交给`agg_loss`，归一化信息在此时就被使用。初始化顺序错误导致第一份 micro-batch 使用局部 token 数，后续 micro-batch 使用 global 分母，下一 outer 的第一份 micro-batch 还会沿用上一 outer 的分母。

设第一个 micro-batch 有$n_1$个有效 token，全 batch 有$N$个 token。正确梯度是

$$
g=\frac1N\sum_{m}\sum_{i\in\mathcal B_m}g_i.
$$

原实现的首次更新在没有 global 信息时得到

$$
\widetilde g=\frac1{n_1}\sum_{i\in\mathcal B_1}g_i+
\frac1N\sum_{m\ge2}\sum_{i\in\mathcal B_m}g_i.
$$

第一份 micro-batch 被放大$N/n_1$倍，这既改变尺度，也改变不同轨迹之间的相对权重。下一 outer 首次 micro-batch 使用$N_{k-1}$而非$N_k$，同样不正确。这是归一化状态错误，与参数精度无关。

修复将`populate_global_batch_info`移到任何 loss 聚合之前，覆盖每份 micro-batch 的 metadata。没有修改 token PG 系数、停止梯度、KL 方向或 outer 同步策略。生产修改保存在`patches/ta-opd-mirror-token-loss.patch`，本机与 archbox 上游运行文件已同步。回归测试`tests/test_training_metrics.py`直接执行真实 entry 函数，并预先注入错误的旧分母 999，验证整 batch 与不等长 micro-batch 划分的 loss 及梯度都等于全 batch 平均。

## 上游配置核对

本次核对 TA-OPD 官方代码[^ta-code]与 One-Shot-OPD 官方代码[^one-code]的固定 commit，沿实际 recipe 到 worker 和 engine 追踪配置。

| 项目               | TA-OPD                | One-Shot-OPD  | 原 MirrorOPD 长程  |
| ------------------ | --------------------- | ------------- | ------------------ |
| 已核对版本         | `62669afb`官方基线    | `6b6b1782`    | run 保存的源码指纹 |
| actor 参数默认存储 | FP32                  | FP32          | 显式覆盖 BF16      |
| FSDP forward 参数  | BF16                  | BF16          | BF16               |
| FSDP reduce/buffer | FP32                  | FP32          | FP32 默认配置      |
| optimizer          | PyTorch AdamW         | PyTorch AdamW | PyTorch AdamW      |
| recipe 学习率      | 参数 LR，可命令行覆盖 | 1e-6          | 3e-7               |

TA-OPD 的`train.sh`没有将 actor 存储改为 BF16，它继承`verl/verl/trainer/config/engine/fsdp.yaml`中的`model_dtype: fp32`。其`transformer_impl.py`构建模型时使用 model_dtype，FSDP 包装时则默认`param_dtype=bf16`、`reduce_dtype=fp32`、`buffer_dtype=fp32`。这表示高精度参数存储配合低精度前向，并非全程 FP32 计算。

One-Shot-OPD 的`recipe/_common.sh`同样没有覆盖 actor 的 model_dtype。`trainer.use_v1=False`进入`main_ppo_v0.py`，该文件仍选择统一的`engine_workers.ActorRolloutRefWorker`，因此不能误认为它使用另一个已经删除的 legacy fsdp_workers 实现。此路径的 FSDP 配置与构建逻辑也保持 FP32 参数存储、BF16 前向。上游提供其他 backend 和 BF16 optimizer 示例，不能据此推广“所有 actor 必须 FP32”。

我们在`training/run_upstream_mirror_training.sh`为了 12GB 环境显式设置了 actor `model_dtype=bfloat16`，改变了上游主 recipe 的参数存储行为。这种覆盖加上普通 AdamW 和很小 lr 存在更新舍入风险。真实模型参数探针已证明这一组合下大量参数没有变化，但不能据此将整个 50outer 效果差只归因于精度。

## 完整框架零更新实验

两次实验均显式使用 BF16 actor、lr=0、B=mini-batch=2、micro-batch=1、J=3、response 预算 128。lr 为 0 排除了参数更新，不受“BF16 小更新舍入”的解释干扰。

| 测试   | 三个 inner 梯度范数  | student center | sampled log-ratio RMS | 最终退出             |
| ------ | -------------------- | -------------- | --------------------- | -------------------- |
| 修复前 | 21、15.1875、15.1875 | 全部 0         | 全部 0                | 1，后续 Ray RAM 保护 |
| 修复后 | 8、8、8              | 全部 0         | 全部 0                | 1，后续 Ray RAM 保护 |

两次 rollout 不保证逐 token 相同，不能把 21 到 8 的差直接作为修复前后降幅。证据是各 run 内部固定权重、固定缓存、相同数据重复 inner 时，修复前第一次范数不同，修复后三次相等。参数未更新时 KL 也没有跳变，因此现有测试不支持把 0.0008 KL 平台解释成纯训练/推理前向底噪。

修复后的训练三次 update 执行完毕，但整个任务仍退出 1。BF16 零更新测试也触发 RAM 保护，说明上次 FP32 FSDP 复验失败不是 FP32 才有的问题；应独立审计模型初始化、CPU 参数/optimizer offload 和阶段切换峰值。没有关闭 Ray 内存保护，也没有把这两次失败标为成功训练。

## 审计边界与后续验证

本次检查了 surrogate 停止梯度、anchor 和 teacher 缓存冻结、sampled token 前驱位置、温度、全 batch/micro-batch 聚合、optimizer step 调用和 scheduler 频率。数学与适配测试通过，没有在这些已测合同中发现新的符号错误。每 outer 结束才推进一次 scheduler，与 outer 预算一致；实际长程学习率全程 3e-7。

仍缺少修复后完整退出的训练复验、FP32 主参数或高精度 optimizer 方案的显存/RAM 验证，以及固定 prefix 当前 student 到 teacher KL。原 50outer 日志已经受到归一化错误与精度覆盖共同影响，不能继续用于判断 J=16、eta=0.3 或该 model pair 是否有效。此前“训练实现正常，主要是 BF16”的判断撤回。保留原结果和诊断，追加明确修订说明，不改写原始数值。
