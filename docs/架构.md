# MirrorOPD 架构

MirrorOPD 的第一方包维护三算法的生产目标、冻结缓存、配置、输入身份、运行生命周期和完成审计。固定版本的 verl 后端承担 Ray 调度、FSDP 训练和 vLLM 生成。源码包、依赖安装、后端准备和模型数据是分开的交付部分；实际操作见[运行与复现](运行与复现.md)。

## 职责边界

| 位置                                                       | 负责内容                                       | 主要约束                                               |
| ---------------------------------------------------------- | ---------------------------------------------- | ------------------------------------------------------ |
| [`core/`](../src/mirroropd/core)                           | 幂均值 reward、概率、缓存、三算法目标与诊断    | 纯张量计算，不依赖 Ray 或 verl；生产损失只维护一份     |
| [`runtime/`](../src/mirroropd/runtime)                     | Job、输入准备、来源、预约、进程、事件和审计    | 从显式配置编排任务，不复制损失公式                     |
| [`integrations/verl/`](../src/mirroropd/integrations/verl) | 布局转换、后端配置编译、更新和评测调用点       | 固定基线及全部必要补丁可重建，框架执行继续复用上游     |
| [`scoring/`](../src/mirroropd/scoring)                     | 数学、数值及自定义任务判分                     | 可独立于 verl 使用；第三方来源和许可证随实现保留       |
| [`reference/`](../src/mirroropd/reference)                 | 独立数学参照                                   | 用于核验生产实现，不作为训练入口或兼容别名             |
| [`profiles/`](../src/mirroropd/profiles)                   | 模型、数据集和训练配方                         | 组合成一份严格且版本化的 Job，不依赖邻仓或父目录 shell |
| [`tests/`](../tests)                                       | 数学、缓存、输入、生命周期、后端合同与维护验证 | 默认由 pytest 收集；真实 GPU 验证另有环境和资源要求    |

[data](../data) 保存支持研究结论的原始证据，[results](../results) 保存统计、图表与验证记录；[experiments/benchmarks](../experiments/benchmarks) 保存可复现验证程序。`runs/` 保存本机运行目录、checkpoint 与 scratch，不纳入 Git。理论来源和工程决策分别位于 [theory](../theory/README.md) 与 [Agent Notes](../.agents/notes/README.md)。

## 配置与准备

[CLI](../src/mirroropd/cli.py) 将配方、模型 profile、数据 profile 和显式变量交给 [Job 解析器](../src/mirroropd/runtime/config.py)。解析器展开变量、补齐默认值、应用已知字段覆盖，再校验类型、版本和跨字段约束。未知字段、缺失变量、非法估计器组合，或不满足 GPU 与 micro-batch 整除约束的全局 batch 都会失败。

`--algorithm` 在上述解析之后应用；`on_policy` 会将每个 fresh batch 的 inner 数固定为 1。配置身份覆盖完整 Job。`plan` 只完成配置层的解析，实际模型、输入和后端还需运行准备阶段核验。

```mermaid
flowchart LR
    A[配方 / 模型 / 数据 / 显式覆盖] --> B[严格 Job]
    B --> C[后端核验与输入准备]
    C --> D[冻结运行源码]
    D --> E[编译 backend.yaml]
    E --> F[资源预约与原生训练]
    F --> G[事件和逐题证据]
    G --> H[完成审计]
```

[输入预检](../src/mirroropd/runtime/preflight.py) 重新计算模型和数据文件的内容哈希，核对 tokenizer、合法词表、共享 chat template、上下文预算、prompt 长度、判分器和验证答案。数据准备接受显式指定的 parquet、JSONL 或 CSV，按配置列映射转换为后端 parquet；它不自动下载数据。题目身份与源文件内容、行号和 split 绑定。

[源码快照](../src/mirroropd/runtime/provenance.py) 保存实际执行的第一方包及后端运行文件，记录逐文件 SHA-256、`source_id` 和环境版本。源码身份不由 commit 名称代替，后续审计重新验证冻结字节。

## 更新窗口与数学对象

一次 outer 表示一批新生成的回答及其固定前缀。学生在窗口开始时作为锚点生成回答，后端打分并构造冻结缓存；随后 inner 更新只重算当前学生相关量。缓存绑定锚点版本、教师与 tokenizer 身份、合法词表、温度、signal 和估计器，过期或不匹配的缓存不能静默复用。

`on_policy` 每个新 batch 只做一次完整更新；`mdpo`、`bpo` 按配方复用同一冻结 batch 多次更新。训练按全局有效 response token 归约，padding 不进入概率运算。完整动作积分只覆盖已经采样的前缀下的合法词表，不枚举全部历史前缀。

[目标实现](../src/mirroropd/core/objectives.py) 将 `score_surrogate` 与 `conditional_objective` 明确区分。冻结 reward 的中心、普通教师 KL 和实际梯度系数也有各自语义；不同对象的前向数值不能直接作为同一损失曲线比较。当前公式与估计器条件见[算法与实现](算法与实现.md)，版本验证证据见[重构说明](2026-10-15-MirrorOPD全面重构说明.md)，理论稿的审定状态仍由 theory 的入口说明约束。

任务正确性由 scorer 产生，用于评测和监测；[后端编译器](../src/mirroropd/integrations/verl/compiler.py) 关闭任务 reward 对当前蒸馏梯度的贡献。修改任务判分与修改训练 reward 是不同的行为变更。

## 后端及进程所有权

[backend.json](../src/mirroropd/integrations/verl/backend.json) 指定上游地址、基线和补丁名，[backend.patch](../src/mirroropd/integrations/verl/backend.patch) 保存该基线之上的全部必要改动。启动前核对实际 HEAD、完整 binary diff 和后端运行目录中的未版本化文件，防止仅凭目录名或可应用补丁误判版本。

0.2.1 的原生验证范围为单机 FSDP、SP=1、rollout TP=1。每个单进程 vLLM executor group 在实际 EngineCore 初始化时使用独立 FileStore；训练进程组使用自己的 store。更大的 executor group 或内部 DP 不在该 FileStore 适配的支持范围。实现边界见 [rendezvous](../src/mirroropd/integrations/verl/rendezvous.py) 与 [executor](../src/mirroropd/integrations/verl/vllm_executor.py)。

运行器在输入准备之后预约显式 GPU，按 PID 与 start-time 验证本任务进程。借用预约需要核对同一暂停 owner，heartbeat 过期不自动转移所有权。退出时清理本任务子进程并检查资源空闲，不执行全局 `ray stop`。相关实现见[预约](../src/mirroropd/runtime/reservation.py)和[进程管理](../src/mirroropd/runtime/processes.py)。

[控制进程管理](../src/mirroropd/runtime/control.py)为前台与后台 CLI 启动同一独立控制进程，日志固定写入 `controller.log`；前台 launcher 转发日志、退出码与终止请求，`--detach` 则返回后由控制进程继续持有生命周期。状态和停止使用主机、PID namespace、PID 与启动时间共同确认所有权，防止共享目录中另一节点的同号 PID 被误用。hope 作业内保持前台等待，使调度器观察任务退出。

[离线传输](../src/mirroropd/runtime/transfer.py)从当前源码和已验证后端生成完整代码包。后端仍以 manifest 和 patch 为开发事实源，发布包携带本地重建的完整 checkout、自包含 Git 对象和自动生成的标准库解包入口；目标机器无需联网。运行证据和 W&B 离线文件以完整快照传输，分片及文件均校验 SHA-256，解包只进入新目录。打包不代表已经下载，不维护隐式确认游标。

后端源码仍通过准备命令获取，未整体纳入主仓库。旧方案中的 subtree、通用 capability planner 和更多生产算法未作为当前接口交付；交付范围的长期理由见[架构决定](../.agents/notes/implemented/architecture/2026-10-12-单仓交付与固定后端.md)。

## 观测与完成条件

每个 producer 单独写结构化事件，rank0 的优化记录来自全局 token 统计。W&B 从同一批记录生成展示，本地事件和原始回答承担审计证据。设备占用与 worker 的 allocated/reserved、计数与秒数、更新前与更新后测量应按各自语义解释。

[完成审计](../src/mirroropd/runtime/audit.py) 同时核对源码与配置身份、退出状态、预期更新坐标、完整 outer 序列、有限统计量、fresh anchor、rollout version，以及每轮逐题样本和评测摘要。缺样本、重复更新或版本不一致会阻止完成；进程返回 0 单独不足以证明成功。

`prepare-only` 到达 `prepared` 后结束，不预约 GPU 或启动训练。它不产生训练完成证据。checkpoint 保存频率可配置，但编译器仍关闭自动 resume；保存文件不能被解释为完整的中断续训协议。
