# MirrorOPD 仓库维护规范

## 当前理论主稿

[固定测度 Token 级 MirrorOPD](../book/2026-10-08-固定测度Token级MirrorOPD.tex) 是本仓库最重要的文档。它组织定义、假设、算法、定理、证明和实验解释。后续理论工作继续修改这份主稿及其 `chapters/` 文件，保持主稿文件名和入口稳定。更新日期记录在正文或 Git 中，不另建日期不同的同主题主稿，也不建立 v2/v3 副本。

章节源文件是具体内容的编辑位置，[PDF](../book/2026-10-08-固定测度Token级MirrorOPD.pdf) 是编译产物，必须与源文件同步更新。修改定义或定理时检查受影响的符号、后续证明、伪代码和实验解释。推导写出中间等式与适用条件，保留完整论证，不以简短总结替代证明。

数学正文与实际算法发生差异时，先写清两者的测度、目标和近似，再修正对应内容。不能为了表面一致而删除假设、省略停止梯度或隐藏估计偏差。2026-10-10 重构前的完整书稿保存在 `docs/book-old/`；早期工程保存在 `docs/earlier/`，用于历史和来源查阅；当前结论在 `docs/book/` 主稿维护。

代码、报告和结果通过链接及配置关联，不放在同一程序目录。已有实验原地完善；新增实验条件使用有意义的配置标识，明确模型、数据或估计方式的区别。主稿文件名固定，其他新文档使用日期加主题命名。

LaTeX 长文按章拆分并用 `\input` 组织，单文件控制在 1000 行以内。

固定监督蒸馏与 BPO 实验总报告按用户要求全部保存在同一个 Markdown 文档，不设千行限制；用章节和段落组织内容，不拆分正文文件。

用户于 2026-10-15 要求另写幂均值生产实现及 Top-J＋tail / 完整词表的正确性对照，维护在 `docs/experiments/2026-10-15-幂均值镜像蒸馏实现与估计器对照.md`。历史优化研究继续维护原总报告，新的实现验证与固定 κ、η 实验写入新报告。二样本 BPO 路线取消，原始历史记录保留，当前代码与执行计划移除相应入口。

## 训练代码与上游边界

生产算法在 `src/mirroropd/training/cache.py` 和 `src/mirroropd/training/losses.py` 维护。缓存负责冻结 rollout 锚点及教师相关量，损失负责 PMD-mean、BPO 和 MDPO 的 inner 目标。`src/mirroropd/integrations/verl/fsdp.py` 对接 verl 张量布局，并显式接收 sequence parallel world size 等框架参数。

TA-OPD/verl 保留 trainer、rollout、actor 更新、checkpoint 和分布式框架。上游的小型 wrapper 查询实际框架状态后调用主仓库适配层。核心损失只维护一份，使 review 和测试可以直接面向主仓库，同时继续使用上游训练链路。

修改按以下顺序进行：

1. 在主稿核对目标、采样测度、KL 方向、停止梯度与同步顺序。
2. 修改 `src/` 核心或适配接口，运行数学、缓存和模型集成测试。
3. trainer 行为需要变化时，修改上游最小集成部分。
4. 按 `upstream-manifest.json` 的 `base_commit` 导出对应补丁。补丁包含相对基线的全部必需修改；导出前检查工作区，排除无关改动。
5. 在干净基线执行 `git apply --check`，实际重放并验证接口。保留第三方来源、版权和许可证。
6. 联合提交核心、接口、补丁、测试与说明，确保新 checkout 恢复相同算法。

manifest 是来源、基线、子模块和补丁路径的维护入口。上游升级需要显式核对接口、重放补丁并测试。忽略目录中的修改不会自动进入主仓库；禁止把唯一一份算法实现留在那里，也不整体复制第三方 trainer。

## 理论与实验证据

估计量明确随机性来自 prefix、rollout token、额外采样还是跨实验重复。KL 数值误差与梯度误差分别定义。bias、variance、RMSE 写明参照 full-vocab KL、聚合权重及是否条件于固定 prefix，避免把 prefix 间差异写成估计方差。

Normalized、Truncated、EMA、Tail-aware 使用各自定义。支持集是谁的 Top-k、是否归一化、尾部如何合并或修正，都写进配置和 metadata。冻结锚点、当前 student 和 teacher 角色保持一致，不仅用一个 `KL` 列名表示多个不同目标。

实验开始前记录待检验命题、判定标准和规模。可引用结果至少关联以下信息：

- 数据与 split、prompt 来源、筛选规则、实际样本数和排除规则。
- student/teacher 版本、tokenizer、温度、top-p/top-k、最大长度和截断情况。
- 算法、估计量、种子、重复次数、outer/inner 步数、同步方式和参数。
- 源码 commit；存在未提交改动时保存差异或文件校验信息。
- 生成命令、输入输出路径、统计定义、单位和绘图脚本。

已有脚本准确表达的内容直接链接，metadata 保存实际运行值。CPU 验证、GPU canary、完整训练和正式 benchmark 分别报告。小模型链路跑通证明实现可执行，不能替代完整 GSM8K 性能比较。现有归档 GPU 运行早于核心代码提取；本次提取后的 CPU 等价性与集成验证不能写成新的 GPU 训练结果。

## 数据与结果管理

原始记录放在 `data/`，统计表和图放在 `results/`。数值图由真实数据和脚本生成，保留轴、单位、聚合方式和样本数说明。重绘时同步更新报告及书稿引用，不手工改图中的数字。

压缩版本化的数据由 `data-manifest.json` 记录原始路径、压缩文件、字节数及 SHA-256。`make data` 恢复原始记录，恢复工具拒绝覆盖校验不一致的现有文件。新增数据时更新 manifest，验证解压内容与原始记录一致。checkpoint 和日志留在 `runs/` 或远端运行目录，支持结论的汇总进入 `results/`。

文件迁移同步更新导入、Shell 路径、Makefile、CI、manifest、文档链接和图片路径。原始数据比较迁移前后 SHA-256；结果检查数值内容和复现命令。程序明确输出路径，避免依赖偶然的当前工作目录。

## 本机与 archbox

三台机器的第一方仓库统一为 `~/src/mirroropd` 和 `~/src/MD-OPD`。后续开发与训练在 archbox 直接进行，源码通过 Git 保存，运行产物留在 archbox。archbox 现有 TA-OPD 后端目录为 `~/src/mirroropd-taopd`，保留其运行环境与上游框架。具体版本及未提交状态见 [三机仓库路径与同步](2026-10-10-三机仓库路径与同步.md)。本机提交不等于远端执行这个版本。

远端运行前同步或安装核心包、应用匹配的集成补丁并同步训练入口。验证远端导入路径、源码版本、模型与数据路径，记录执行命令。部署记录包含核心 commit 和上游基线，避免旧核心与新 wrapper 混用。启动入口通过 `PYTHONPATH` 加载核心包；远端位置不同可使用 `MIRROROPD_SRC_ROOT`。部署必须包含完整的第一方包和更新后的补丁，仅复制 launcher 不足以更新算法。

模型缓存、大数据、checkpoint 和 scratch 使用项目忽略目录或 `~/.cache/` 等磁盘位置。archbox `/tmp` 是容量受限的 tmpfs，不用于大文件下载、数据解压或训练 scratch。迁移计算位置时保留相同配置和证据记录。

## 检查与提交

初始化和检查从仓库根运行：

```bash
make bootstrap
make upstream
make data
make test
make book
make check
```

按变更范围选择必要检查。纯文档排版不要求重跑 GPU 训练；核心损失、缓存和同步变化需要数学与模型集成测试，再按风险运行 GPU canary。书稿与图片引用变更需要编译并检查输出。测试通过后不机械扩大验证；新失败或未解决的疑点继续定位。

`make check`、提交 hook 和 CI 使用同一套仓库配置。Python 使用 Ruff；Shell 使用 shfmt/shellcheck；Markdown 使用 markdownlint、autocorrect/prettier；YAML 检查注释宽度；配置 JSON/TOML 使用 prettier/taplo；Actions 使用 actionlint；凭据使用 gitleaks。原始实验数据保持语义和校验关系。

提交使用英文 Conventional Commits，一个提交处理一个逻辑变化。代码和必要的测试、补丁及说明共同提交。纯格式化单独提交，hash 记入 `.git-blame-ignore-revs`。精确暂存本次文件，保留他人的未提交工作。

`AGENTS.md` 和 `.agents/` 是入库的 agent 入口。`.claude/skills/` 及预览链接为本机便利层，通过 `scripts/agent-links.sh` 和 `scripts/crossnote-links.sh` 重建。维护规范、命令或目录结构变化时同步更新入口说明，使新 checkout 的使用路径与实际实现一致。
