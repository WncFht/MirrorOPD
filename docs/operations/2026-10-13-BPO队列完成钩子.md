# BPO 队列完成钩子

## 触发与产物

完成钩子附着到现有 scalar_queue_handoff supervisor，使用 Linux pidfd 等待该进程退出。等待期间阻塞在退出事件上，没有定期读取训练日志、GPU 状态或 worker 进度。supervisor 覆盖当前全量校准、阶段分叉、三种子确认、旧确认收尾、长轨迹复验和旧消融，因此触发时点是整个现有队列结束，不是单个 worker 结束。

用户取消后续多 seed 确认后，钩子改为附着到 --remaining-only --skip-confirmation 的 scalar_full_pool_study controller，等待其长轨迹复验与单 seed 消融队列退出。user-amendment.json 保留取消理由与范围；completion.json 同步记录这项调整，产物完整性检查排除明确取消的两个确认阶段。原先已经完成的确认记录继续保留并生成 CPU 报告。

队列退出后，钩子一次性核验预登记条件的 summary、审计终点、配置及全 pool backward 计数。它同时补算 CPU 报告，包括当前运行中的旧 controller 尚未加载的三种子配对分析。报告写入 results/scalar-large/completion-reports，状态文件写入 runs/scalar-large/completion-hook/completion.json，阅读入口为同目录 ready.md。

所有预期实验产物完整时，状态为 experiments_complete。条件失败、缺失或报告生成失败时，状态为 needs_review，并逐项记录问题。该标记表示实验队列的产物状态；最终科学分析、文档收束和研究目标完成仍需后续核验。钩子不启动或重启训练，不生成新 rollout，不改变现有 optimizer，不启动 teacher/student/domain 扩展矩阵。

armed.json 记录已附着的 supervisor 身份和钩子 PID。pidfd 绑定具体进程，后续 PID 复用不会将退出事件切换到另一个进程。启动时再次核对身份，防止附着期间发生进程替换。

## 启动与后续阅读

入口是 training/scalar_completion_hook.py。使用当前环境的 Python，从仓库根目录启动以下命令，并将 stdout/stderr 保存在钩子目录。这里的 supervisor PID 应取本次实际已确认的进程，不能复制过期 PID 后直接启动。

```bash
python -m training.scalar_completion_hook \
    --pid SUPERVISOR_PID \
    --root "$PWD" \
    --output runs/scalar-large/completion-hook
```

正式附着通过独立后台进程执行，当前训练继续运行。后续回来先读 completion.json 与 ready.md，再读 completion-reports 中的完整误差、阈值成本和配对比较。等待事件期间没有自动 Git 提交；结果分析完成后再分批提交可复现交付物。

钩子只写本地结果文件，不发送邮件或消息。CPU 测试覆盖真实子进程退出事件、错误 full-pool backward 计数，以及 supervisor 退出但产物缺失时必须标记 needs_review。
