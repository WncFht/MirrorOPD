# 统一 OPD 工程与开源维护

## 设计依据

算法契约采用 [统一抽象方案](../2026-10-10-OPD统一抽象与MD-OPD接入方案.md) 的分布身份、候选身份、评分需求、梯度程序和更新窗口。工程实现围绕这些对象组织，不从某个 fork 的配置字段反推算法。不同仓库的论文目标、实际 gradient recipe 和运行条件分别核对。

当前源码已包含配置化 launcher、resolved Hydra config、源文件 SHA-256、inner/outer JSONL、W&B 展示映射、GPU 采样与阶段主存诊断。统一设计应保留这些能力，修正缺少算法身份、实际 optimizer update 轴和分布版本检查的部分。

本机工程阅读入口为 `training/run_configured_training.sh`、`training/record_training_provenance.py`、`src/mirroropd/training/metrics.py`、`tracking.py` 与 `host_memory.py`。本文是接入方案，不修改现有训练任务。

## 评分需求决定执行成本

先编译 objective 的评分需求，再决定模型执行计划。sampled MDPO、head-tail BPO 和 live full-center residual 的成本不同，不应全部调用同一个 always-full diagnostics forward。

| Recipe                   | outer 冻结内容                                       | inner live 内容                           | 额外注意                                    |
| ------------------------ | ---------------------------------------------------- | ----------------------------------------- | ------------------------------------------- |
| sampled reverse-KL score | behavior 与 teacher action LP                        | current action LP                         | 旧 proposal 需要 action IS                  |
| Mirror MDPO              | anchor/teacher action LP                             | current action LP                         | head/tail 仅为可选诊断                      |
| Mirror Mean              | action LP、teacher center                            | current action LP                         | center 的精确性改变目标                     |
| Mirror BPO               | action LP、anchor head/tail、teacher center          | current action/head/tail                  | current center 每次重算，coefficient 停梯度 |
| MOPD live residual       | anchor state evidence、teacher state evidence        | current action 与 live anchor expectation | 不能把 live expectation 放入 detached RPC   |
| coarse teacher KL        | teacher-selected IDs、teacher head/tail              | current head/tail                         | 分区目标直接反传                            |
| HETS/ResOPD/SC-TA        | teacher-selected support 与 teacher action/head/tail | current action/head/tail 与 surrogate     | deterministic 与 stochastic 项分别处理      |

相同评分可以被不同 recipe 复用，评分自身不包含 reward 解释。需求缓存键至少包含 distribution version、layout ID、support hash、temperature/action transform、dtype 和 required outputs。模型名相同不足以共享缓存。

## 显存与主存的成本模型

对一个 micro-batch，完整 logits 的最低存储是 $N V b$ 字节，$N$ 为实际经过 LM head 的 prediction 数、$V$ 为词表大小、$b$ 为 dtype 字节数。full logits、float32 log-softmax、概率、teacher/student 临时张量和 autograd 保存量会叠加。

例如 N=2048、V=151936 时，一份 BF16 logits 为约 0.580 GiB，一份 FP32 为约 1.159 GiB。这里还没有加入模型权重、activation、optimizer、KV cache、FSDP all-gather 和 CUDA workspace。缓存只存 N×K 并不使全部计算降为 O(NK)：normalizer 与全局 Top-K 仍要扫描完整词表。

第一项优化是只对有效 response prediction 计算所需 logits，避免 prompt/padding 的无用 LM-head 输出。第二项是复用一个 full-vocabulary normalizer 和指定 IDs gather，减少 full log-softmax/probability 副本。第三项是按 token 与 vocabulary 分块；真正避免 N×V materialization 需要 tile 化 LM-head 和相应 backward，不能在 full logits 已生成后才切块并称为解决峰值。

精确 $E_q\log p$ 需要完整 anchor 权重与当前 log probability 的配对。只存 head/tail 不能恢复该积分。可选方案是保存完整 frozen anchor evidence、重新执行冻结 anchor、或使用经过验证的 paired/tiled reduction；它们分别消耗主存/通信、计算和 backend 开发成本。选择近似 center 是算法变化，不能作为透明内存优化。

温度变换后的 normalizer必须在目标分布上重算。有限 teacher-own Top-K 无法恢复任意温度的全词表 normalizer。TP 下使用全局 logsumexp 和全局 token IDs；每 shard 的 local Top-K 不能直接解释为全局支持集。

### 内存阶段与资源所有权

至少划分 rollout、anchor scoring、teacher scoring、actor forward/backward、optimizer、weight sync、evaluation、checkpoint 八个阶段。每个阶段声明需要常驻的模型、KV cache、frozen evidence 与 buffers；phase transition 明确释放 owner，不依赖 Python 垃圾回收的偶然时机。

actor/reference/teacher 的参数 offload、optimizer offload 与 inference sleep 是独立开关。参数卸载降低显存，却增加 CPU/pinned 主存和 PCIe 传输；低显存设备不应默认卸载所有模型。FSDP full-state export/hard sync 的瞬时 GPU 与主存峰值单独测量。

Ray object store、worker Python heap、共享页、pinned cache、FSDP CPU gradients、tokenizer/dataloader 和重复 teacher worker 都进入主存预算。多个进程 RSS 相加会重复计算共享页，报告 PSS/USS、system available、swap 与 Ray object store 使用。容量 admission 依据每阶段峰值和余量，不仅看 nvidia-smi 静态空闲。

### 当前 archbox 的现场证据

2026-10-10 本次只读检查时，archbox RTX 4070 SUPER 总显存 12282 MiB，已用 8101 MiB，GPU utilization 53%。主存 31 GiB、available 7.5 GiB，swap 已用 7.3 GiB。磁盘可用 74 GiB；16 GiB tmpfs `/tmp` 已用 16 MiB。`main_ppo` 进程和 `gsm8k-smollm2-opd-onpolicy-o100-j1` launcher 均存活，运行约两小时。

这些数据是当时的资源快照，不是 memory benchmark。本次不向正在训练的 GPU 再投放竞争任务。未来性能实验进入独占队列，记录开始时的其他进程、hardware 与系统余量；模型下载、Ray scratch 和 checkpoint 使用磁盘目录。

## 精度与数值稳定

区分模型参数、activation、logits、normalizer、probability mass、loss reduction、gradient accumulation、optimizer master state 和 cache dtype。不能用一个 `model_dtype` 代表整条数值链。归一化、tail mass 与全局 sum/count 优先在 FP32 累积；数学 oracle 使用 FP64。

tail 使用稳定 log1mexp，并对 empty/full support 分支显式处理。概率质量合法性与数值修正分别记录；任意 mass floor/clamp 都可能改变 value 和 gradient，应成为 numerical policy，报告激活次数和阈值。importance ratio 的 overflow、KL 函数 clipping 与 optimizer gradient clipping 分别观测。

验证分三层：相同 dtype 的 legacy parity；FP64 oracle 对生产精度的误差；两个 scoring backend 对相同模型与 token 的数值差异。vLLM 与 FSDP 在同一权重下的 action LP 差异属于 proposal 契约误差，不能由高相关系数替代最大偏差、分位数和长轨迹累积分析。

## 部署与复现

每次运行先 resolve 配置、编译 objective plan 和 score requests、验证 tokenizer/action space、backend 能力、数据 schema、资源余量与 source provenance，再启动 Ray/GPU。失败应发生在训练之前，不在第一个 teacher RPC 后才暴露不支持的算法组合。

release manifest 固定第一方 commit、上游 commit、patch SHA-256、Python/PyTorch/CUDA/vLLM/Ray 版本、wheel ABI、模型/tokenizer revision、数据 SHA-256 和完整 resolved config。源码 dirty 时保存实际差异或文件哈希；仅存 commit 无法说明运行了什么。

运行采用不可变 source snapshot 和唯一 run ID。升级以新 snapshot 部署，通过 canary 后再切换下一次任务；不修改正在执行的 launcher、源码或环境。archbox 作为运行位置，源码通过 Git 保持版本，结果留在远端并发布经过筛选的 evidence。

环境分 CPU oracle、受支持的 FSDP/vLLM 组合和可选 Megatron/Slime 三类。每个 backend 有明确版本矩阵，基础包不强制安装 CUDA/Ray。公开容器或锁定环境记录必须经实际 import、模型 forward、rollout 与权重同步验证；依赖解析成功不等于 ABI/API 兼容。

checkpoint manifest 明确 cold、outer-boundary 或 exact-window 等级。恢复顺序是配置和模型、optimizer/scheduler/RNG、distribution snapshots、window/replay、rollout sync；不支持的 mid-window resume 应拒绝。原子写入、完整性校验和 retention 删除分别执行，不能把半写 checkpoint 当作可恢复状态。

## 可观测性

JSONL 是本地可恢复事实记录；W&B 是可选展示后端。metric schema 版本化，始终区分 surrogate loss、真实 objective、KL value 与梯度诊断。不能从 stopped-score surrogate 的正负判断 KL 是否下降。

| 指标组         | 必须包含                                                                                                        |
| -------------- | --------------------------------------------------------------------------------------------------------------- |
| 身份与生命周期 | run ID、outer/window、实际 optimizer update、micro-batch、behavior/anchor/teacher/rollout version、support hash |
| 数学与近似     | direction、target/proposal、support resolution、center error、scalar/gradient bias 的 oracle 子样本             |
| off-policy     | log-ratio 分位数、ESS、missing support、cap/clip 激活、proposal/scorer 差异                                     |
| 支持集         | K、有效/重复 IDs、head/tail mass、student/teacher overlap、sampled action 是否在 head                           |
| 优化           | raw gradient norm、clip scale、post-clip norm、learning rate、eta、coefficient 分位数、非有限值                 |
| 数据与质量     | prompt/response 长度、终止/截断比例、实际 token 数、reward/eval、过滤与 replay 权重                             |
| 性能           | 每阶段时间、scoring 次数、payload bytes、tokens/s、GPU allocated/reserved、RSS/PSS/USS、pinned、swap            |

实际 optimizer update 是主轴，不能用 `outer×epochs+inner` 推定：mini-batch 数、gradient accumulation、shuffle 与跳过更新都会改变对应关系。生成 token、训练 token、teacher-scored token、wall time 和 eval sample 数作为独立预算轴。

多 rank 记录由单 writer 聚合或使用 rank-specific files；每条 event 有唯一 ID。上传支持断点和幂等去重，不能靠内存里的已读行数承诺跨进程 exact-once。主存诊断依赖 Linux `/proc` 与部分 PyTorch private binding，作为可选 backend capability，失败不能中止数学训练。

异常至少区分 resource admission、proposal/support、distribution version、NaN/Inf、collective schedule、teacher timeout、sync 和 checkpoint。默认保留原始字段、配置和前后阶段快照，避免只有一个最终 OOM 字符串。

## 开源维护与兼容策略

公开 API 只承诺数据契约、纯 tensor kernels 和有限 recipe registry；backend adapter 版本与框架绑定。保留独立数学 oracle，避免被测 kernel 与 oracle 共享全部公式。新增算法提交必须包含目标、value/backward 配对、proposal/support 假设、数据需求、数值边界、benchmark 和可运行配置。

维护矩阵至少覆盖 Python CPU 导入、finite-vocab oracle、cache/window、layout、micro-batch reduction、固定上游 adapter 与 patch replay。GPU CI 作为明确的 scheduled/manual gate，测试真正的 forward、rollout、update、sync 与 boundary resume。TP/SP 扩展使用真实多 rank 检查，不能由单 rank tensor stub证明 collective 正确。

单独保存 third-party notices、license 与来源。传统 MDPO 当前仓库没有 LICENSE/COPYING，应只参考论文数学独立实现，避免复制源码。其他仓库及其 vendored/submodule licenses分别核对，顶层 license 不能自动覆盖所有第三方内容。

新增或删除配置采用 schema version 与迁移说明。含歧义的历史模式保留 `legacy` recipe 和 golden evidence，不静默映射到新目标。旧 fork 的补丁仅承担最小集成，定期在固定 clean base 重放；不整体维护多份 trainer。

本次在隔离 checkout 执行 `npm ci --ignore-scripts` 和 `npm audit --json`，现有开发工具锁文件报告五个 high 条目，来源是 braces 深度嵌套 pattern 导致 stack-exhaustion 的 advisory，经 micromatch、fast-glob、globby 传播到 markdownlint-cli2。这是开发工具依赖审查结果，不表示训练服务已遭利用。audit 自动建议将 markdownlint-cli2 降到0.0.4，不能直接执行破坏性 `audit fix --force`；开源发布前须独立验证修复版本、工具输出与攻击入口，并更新锁文件和工具链测试。本轮保留现有依赖，不把依赖修复混入算法方案。

## 性能验证顺序

先以固定真实 prefix/logits比较 score query、full/coarse center 和 estimator：数值/梯度一致后测 peak GPU/CPU、payload 与 latency。在同一独占硬件重复至少五次，分别报告 cold/warm、median/range。再验证多 outer/inner、sync 与恢复，最后比较训练质量。

正式算法比较同时对齐生成 token、optimizer update、teacher scoring 成本和 wall time。增加 K 会改变信息量、目标或 estimator，不仅改变速度；只对齐 outer step 会掩盖不同成本。算法效应、精度效应、batch/reduction效应和硬件优化分开消融。
