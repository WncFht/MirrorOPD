# 运行与复现

本指南面向使用当前 0.2 接口的开发者。一次运行依次完成配置解析、后端与输入核验、源码冻结、资源预约、原生训练和完成审计。当前入口统一为 `mirroropd`；旧版实验的复现条件在各实验报告中单独说明。

任务 profile、自动运行身份、原生优化器与 checkpoint 参数，以及 study 的参数展开、汇总和失败重试见[实验配置与批量运行](实验管理.md)。旧的显式模型、数据和配方选择继续可用。

## 环境与输入

使用 Python 3.12 的独立环境。已有 GPU 软件栈时，先核对兼容性再安装本包；数据转换、测试和数学判分依赖可用下面的命令安装：

```bash
python -m pip install -e '.[data,backend,math,tracking,test]'
python -m mirroropd --version
```

[pyproject.toml](../pyproject.toml) 声明本包及 extras 的依赖范围，不是完整 CUDA 环境锁。GPU 运行还要求匹配的 PyTorch、vLLM、FlashAttention、Ray、TensorDict 和系统驱动。本机`environments/`可保存环境清单和 wheel 校验记录，该目录不随 Git checkout 交付。每次运行应保存实际依赖版本与来源；清单本身不能证明新机器上的 ABI、安装和 GPU 执行有效。维护工具的安装另见[开发维护指南](maintenance.md)。

内置 `deepseek-justrl` 模型 profile 要求显式 `model_root`，下面有学生 `DeepSeek-R1-Distill-Qwen-1.5B` 与教师 `JustRL-DeepSeek-1.5B` 的本地 Hugging Face artifact。模型须含 config、tokenizer 和权重，具有相同 token-to-ID 语义、特殊 token 与共享 chat template；目录同名不足以证明权重相同。没有合适的共同模板时，应显式配置 `models.chat_template`。

内置 `dapo-math` 数据 profile 从 `data_root/math/` 读取 DAPO 训练集及 MATH-500、AMC23、AIME25 验证集；具体路径以[模型 profile](../src/mirroropd/profiles/models/deepseek-justrl.json)和[数据 profile](../src/mirroropd/profiles/datasets/dapo-math.json)为准。可改用自己的 JSON profile 或已知字段覆盖。当前数据准备消费已有 parquet、JSONL 或 CSV，不提供自动下载入口。

验证集默认要求参考答案，训练集大小须覆盖一个完整 prompt batch。输入准备核对内容哈希、列映射、prompt 长度、词表和上下文预算。历史训练测试重叠、去重版本和解码协议的差异应在实验记录中保留；换数据不等于复现原有成绩。

## 配置解析

从仓库根执行，示例的 `/models` 与 `/data` 是占位路径。`plan` 不读取这些路径或检查 GPU：

```bash
mirroropd plan --recipe math-four-gpu --models deepseek-justrl --dataset dapo-math \
  --var model_root=/models --var data_root=/data --algorithm on_policy \
  --set logging.wandb.enabled=false --output runs/plan-on-policy.json
```

配方先组合模型和数据 profile，再展开显式变量、补齐默认值、应用 `--set`，最后校验 Job。缺失变量不从环境中推断。`--set` 的值先按 JSON 解析，未知路径、未知字段、类型不符或旧 schema 会被拒绝。

`--algorithm` 在 Job 解析后选择生产算法，选择 `on_policy` 时将 `training.inner_steps` 固定为 1；`mdpo`、`bpo` 沿用配方的 inner 设置。直接通过 `--set objective.algorithm=on_policy` 修改字段仍须满足 Job 的一次更新约束。完整默认值与展开结果以当前 `plan` 输出为准，不用旧 Hydra 字段覆盖新 Job。

`math-four-gpu` 配方默认开启 W&B；例子显式关闭云端记录，本地证据仍保留。`plan`、`run` 和 `suite` 都接受 `--wandb online|offline|disabled`，该参数在 `--set` 后应用。`online` 启用在线记录，`offline` 在本地保存供后续上传的 SDK 文件，`disabled` 关闭 W&B。等价配置为 `logging.wandb.enabled` 与 `logging.wandb.mode=online|offline`；关闭时 `enabled=false` 优先。凭据使用账号环境，不放入配方、Git 或日志。

W&B 的工作、cache 和 artifact staging 目录分别固定在运行目录下的 `wandb/`、`wandb-cache/`、`wandb-data/`。运行器按配置设置子进程的 `WANDB_MODE`，不会从父 shell 的同名变量推断模式。算法由 `--algorithm` 独立选择，W&B 离线模式不改变训练算法。

## 缓存与显存配置

`memory` 是 Job 的严格配置部分，随 `plan` 展开并进入配置身份：

| 字段                        | 默认值              | 控制范围                                                       |
| --------------------------- | ------------------- | -------------------------------------------------------------- |
| `cache_bytes`               | 2147483648（2 GiB） | 最终冻结 cache payload 的容量上界                              |
| `scoring_buffer_bytes`      | 67108864（64 MiB）  | 单次评分输出 tile 的保守 staging 预算                          |
| `token_chunk_size`          | 64                  | 有效前驱位置的投影／损失分块                                   |
| `vocab_chunk_size`          | 4096                | 完整 BPO 无诊断及 hidden sampled BPO 的词表分块                |
| `anchor_storage`            | `log_probs`         | 默认完整概率证据；`hidden` 仅用于完整中心的 sampled BPO        |
| `projection`                | `chunked`           | `chunked` 或原生完整输出的 `eager`                             |
| `profile_phases`            | `false`             | worker 操作边界同步、重置及读取 CUDA 峰值                      |
| `teacher_parameter_offload` | `null`              | `null` 继承 training parameter offload；布尔值单独控制 teacher |

缓存预算在模型合法词表确定后、预约 GPU 前检查，使用最大 response action 数估算完整字段，并计入序列位置上的标量／Top-J 元数据。实际评分再次检查有效数。超预算会拒绝运行，可降低 batch／长度或显式提高缓存预算；改变 center/integration 会改变估计器，应另立实验。`inputs.json` 中的 `memory_plan` 保存容量计划。

`cache_bytes` 与 `scoring_buffer_bytes` 均不限制整个进程或 GPU 分配器。模型、优化器、参数梯度、backbone activation、词表投影临时空间、运输及拼接副本另占内存。减小 token chunk 可降低一般路径的投影临时空间，代价是更多调用与反向重算；默认完整证据仍为 $N\times V$。诊断策略也影响计算量，完整 BPO 的二维投影仅在 `diagnostics=none` 启用。

以下命令只验证配置展开，可将相同字段用于 `run`：

```bash
mirroropd plan --recipe math-four-gpu --models deepseek-justrl --dataset dapo-math \
  --var model_root=/models --var data_root=/data --algorithm bpo \
  --set memory.token_chunk_size=16 --set memory.vocab_chunk_size=2048 \
  --set memory.cache_bytes=4294967296 --set memory.teacher_parameter_offload=true \
  --set memory.profile_phases=true --output runs/plan-memory.json
```

`chunked` 要求 SP=1、remove-padding 和非 fused head，只支持标准 Qwen2/Qwen3/Llama/Mistral 线性 LM head，其他输出合同会报错；显式设置 `memory.projection=eager` 使用完整原生 logits 路径。两条路径共用目标和冻结合同。profiling 会同步 CUDA 并影响耗时，日常运行保持关闭；当前实现的 CPU 数值证据与 GPU 验证状态见[实现对照报告](experiments/2026-10-17-幂均值镜像蒸馏实现与估计器对照.md)。

`hidden` 使用最终归一化后的 anchor hidden 和冻结 head。head 由 actor rank0 在 FSDP forward 中截取合法词表后保存到 `cache/anchor-heads/<outer>.pt`，原子发布；driver 等待整个 anchor pass 完成才启动 teacher。actor／teacher worker 各缓存至多一份 host head，每个 forward 同步搬到当前设备，用完释放 GPU 引用。下一 outer 开始后删除旧 head 文件；同版本文件已存在则拒绝，当前不支持等价恢复。所有角色须访问同一运行目录；该文件是运行缓存，不是可独立迁移的模型 checkpoint。

容量预算包含 hidden、归一化标量、原有元数据和一份共享 head，head 按可能存在 bias 保守计量。多 rank 的 host head 副本、序列运输副本与瞬时 GPU head 另行计量。该路径已通过 CPU 数值与真实 Qwen2 接线验证；四卡 GPU canary 尚未完成，保持显式启用，验证范围和 CPU 耗时代价见[调研及实现报告](analysis/2026-10-18-DeepSeek-V4蒸馏显存方案与开源实现调研.md)。

展开配置可执行：

```bash
mirroropd plan --recipe math-four-gpu --models deepseek-justrl --dataset dapo-math \
  --var model_root=/models --var data_root=/data --algorithm bpo \
  --set objective.estimator.center=full --set objective.estimator.integration=sampled \
  --set memory.anchor_storage=hidden --output runs/plan-hidden.json
```

## 后端准备与版本核验

```bash
make upstream
```

此命令通过包内 [backend.json](../src/mirroropd/integrations/verl/backend.json) 获取固定基线，并应用与当前包匹配的 [backend.patch](../src/mirroropd/integrations/verl/backend.patch)，默认输出到 `upstream/TA-OPD-v2`。也可以显式指定新的目录：

```bash
mirroropd backend --output upstream/my-pinned-backend
```

启动前核对实际 HEAD、完整补丁差异及后端运行源码中的未版本化文件。旧补丁或其他本地修改会被拒绝；出现冲突应保留原目录并换新目录重建，不覆盖正在执行的后端。更新到 0.2.1 后不能因目录名称相同就复用 0.2.0 的准备结果。

后端准备与安装 GPU 依赖是两件事。`make data` 只恢复 [data-manifest.json](../data-manifest.json) 登记的压缩研究证据，不下载模型或生成内置 profile 所需的全部训练输入。

## 不启动训练的准备检查

模型、数据和匹配的后端准备好后，将路径替换为实际位置，并使用一个尚不存在的输出目录：

```bash
mirroropd run --prepare-only \
  --recipe math-four-gpu --models deepseek-justrl --dataset dapo-math \
  --var model_root=/models --var data_root=/data --algorithm on_policy \
  --set training.outer_steps=2 --set evaluation.question_limit=4 \
  --set logging.wandb.enabled=false \
  --backend upstream/TA-OPD-v2 --output runs/my-prepare

mirroropd status runs/my-prepare
```

成功状态为 `prepared`。此时已有输入核验、规范化数据、冻结源码和 `backend.yaml`，尚未预约 GPU 或启动 Ray、FSDP、vLLM。`prepared` 不能证明模型推理、反向传播、显存容量、权重同步或训练完成，也不能对该目录要求完整训练审计。

`inputs.json` 记录实际模型、数据、词表和评测协议身份，`job.json` 保存准备后解析的绝对输入路径；实际运行配置可能因此与仅解析相对路径时的 `config_id` 不同。复现时比较运行中保存的身份，不只比较启动命令文本。

## 小规模训练与审计

GPU 软件栈和可预约设备满足要求后，使用另一个新目录运行小规模链路检查：

```bash
mirroropd run \
  --recipe math-four-gpu --models deepseek-justrl --dataset dapo-math \
  --var model_root=/models --var data_root=/data --algorithm on_policy \
  --set resources.gpu_ids='[0,1,2,3]' \
  --set training.outer_steps=2 --set evaluation.question_limit=4 \
  --set logging.wandb.enabled=false \
  --backend upstream/TA-OPD-v2 --output runs/my-canary

mirroropd status runs/my-canary
mirroropd audit runs/my-canary
```

`resources.gpu_ids` 明确物理设备身份，并须满足全局 batch、micro-batch 和 GPU 数的整除约束。检查可用资源时不得清理其他任务。单机 FSDP、SP=1、rollout TP=1 是当前验证范围；FileStore 的单进程推理组适配不能推广为多机或更大 executor group 的支持承诺。

两轮、四题检查仍沿用配方的生成长度和每题采样数，可能有明显 GPU 成本；它只检验小规模执行链路，不代表完整数据集成本或算法质量。正式实验应冻结代码、输入、评测和预算，按已完成 outer、实际更新次数与运行时间分别比较。

`status` 读取运行状态；在相同主机和 PID namespace 中，若控制进程身份已失效，会把仍标为运行中的状态报告为 `orphaned`。通过共享目录在另一节点查看时，保留记录状态并报告 `process_check=other_host_or_namespace`。旧状态没有主机身份时报告 `unavailable`，不能据本机同号 PID 判断其存活。`audit` 重新核对冻结源码、配置、退出状态、更新序列、rollout version 和逐题评测，并写 `verification.json`。配置身份按持久化的 `job.json` 内容计算，新增默认字段不改写旧运行身份。只有完整审计通过才能计为完成，退出码 0 不足以替代审计。

`suite` 使用相同 Job 顺序执行所选算法，每组有独立子目录，失败即停止。它沿用配方各算法的实际更新预算；相同 outer 数不表示相同优化次数或耗时。

## 后台启动与日志

`run` 和 `suite` 都启动独立控制进程，将其 stdout 和 stderr 写入输出目录的 `controller.log`。默认前台等待并转发日志、退出码和停止信号；增加 `--detach` 后立即返回控制进程 PID、主机身份和日志路径。后台控制进程通过 `nohup` 和新会话启动，标准输入关闭，终端断开不会终止它。后台启动成功不代表训练成功，使用 `status` 和完成审计判断结果。

下面使用短配方完成两轮链路检查，输出目录必须尚不存在：

```bash
mirroropd run --detach \
  --recipe smoke --models deepseek-justrl --dataset dapo-math \
  --var model_root=/models --var data_root=/data \
  --algorithm on_policy --wandb offline \
  --backend upstream/TA-OPD-v2 --output runs/smoke-background

tail -f runs/smoke-background/controller.log
mirroropd status runs/smoke-background
mirroropd stop runs/smoke-background
```

`controller.json` 记录控制进程的 PID、启动时间、主机和 PID namespace；`controller-exit.json` 记录控制进程退出码。`backend.log` 独立保存 Ray/FSDP/vLLM 的 stdout 和 stderr，`events/` 与逐题结果继续承担审计证据。`suite` 的控制日志和控制进程记录位于组目录，后端日志位于各算法子目录；停止 suite 应指定组目录。

`stop` 只向身份匹配的本地控制进程发送 SIGTERM，等待其清理后端和释放预约；默认等待 30 秒，可用 `--timeout` 调整。超时报告仍在停止，保留现场，命令不升级成全局清理或强杀。来自另一节点、容器 PID namespace 或旧版本的控制记录不能证明本地所有权，需在实际执行节点处理。直接终止前台 launcher 也会请求控制进程停止；正常退出码随控制进程返回。

## 离线代码与结果传输

有网络的准备机先生成匹配后端，再打包运行源码。`pack code` 包含第一方源码、配置、脚本、测试、工程文档，以及已应用补丁的完整后端。后端通过本地 Git clone 重建，携带独立对象库并去掉 origin；它不携带原 checkout 的 Git 配置和私有 hooks。目标机无需访问 GitHub 或重新应用补丁，运行时继续核验固定基线和完整 diff。模型、数据、依赖 wheel 与研究证据另外传输。

```bash
mirroropd pack code --backend upstream/TA-OPD-v2 --output transfers/code-v02
```

将整个 `transfers/code-v02/` 上传到开发机，包括 `manifest.json`、全部分片和自动生成的 `bootstrap.pyz`。首次解包直接使用 Python 标准库，无需先安装 MirrorOPD：

```bash
python /uploads/code-v02/bootstrap.pyz unpack /uploads/code-v02/manifest.json --output /shared/releases/v02
cd /shared/releases/v02/MirrorOPD
python -m pip install --no-deps -e .
python -m pip install --no-deps -e upstream/TA-OPD-v2/verl
python -m pip check
```

`bootstrap.pyz` 由当前 CLI 源码生成，`unpack` 路径只依赖 Python 标准库；已有 CLI 时也可直接使用 `mirroropd unpack`。安装步骤中的依赖须已在该环境准备好；完全无包索引的机器另行携带匹配 wheel，并通过 `pip --no-index --find-links` 安装。代码包的 `environment.json` 是打包环境库存，不等同于目标镜像验证或完整依赖锁。

回传完整运行证据或只回传 W&B 时，分别执行：

```bash
mirroropd pack results --run runs/smoke-background --output transfers/result-001
mirroropd pack wandb --run runs/smoke-background --output transfers/wandb-001
```

结果包保存运行目录中的源码快照、配置、规范化数据、日志、事件、逐题回答及 W&B 文件；checkpoint、cache、staging、临时 Python 缓存和便捷软链除外。大文件完整保留，不设置 100 MB 静默跳过阈值。W&B 包仅保存运行目录中的 `wandb/` 和 `wandb.json`；它不包含完整审计证据。支持 suite 根目录。活动任务的包在 manifest 中标记 `live_snapshot=true`，其中跨文件记录可能处于不同进度，不能当作训练完成证据。

手动下载完整包目录后，在本地使用新目录解包。离线 SDK 文件上传云端是显式操作：

```bash
mirroropd unpack /downloads/result-001/manifest.json --output imported/result-001
mirroropd unpack /downloads/wandb-001/manifest.json --output imported/wandb-001
wandb sync imported/wandb-001/runs/smoke-background/wandb/wandb/offline-run-*
```

SDK 通常在指定工作目录内再建一层 `wandb/`；以解包后实际的 `offline-run-*` 目录为同步对象。建议等 SDK 完成写入再上传。解包命令不自动登录或调用云端同步，上传失败时原文件和分片仍保留。

每包为完整快照，默认按 10 MiB 分片，可用 `--chunk-bytes` 调整。manifest 逐项记录分片和文件大小、SHA-256、包类型及快照状态。缺失、损坏、重复成员、路径越界和软链接成员都会阻止解包。重组与暂存使用磁盘 cache，解包只发布到新目录；输入归档、旧快照和活动目录均保留。打包不推进“已下载”游标，每次可独立重传。校验用于检验传输完整性，不代替可信渠道的来源认证。

Makefile 提供 `code-pack`、`results-pack`、`wandb-pack`、`unpack`，通过 `PACKAGE`、`BACKEND`、`RUN`、`MANIFEST` 和 `DEST` 传参；这些命令与 CLI 使用同一实现。直接运行 `make` 或 `make help` 查看入口，书稿仍用 `make book` 显式构建。解包后可执行 `make wandb-sync WANDB_RUN=.../offline-run-...`，其中 `WANDB_RUN` 是一个实际存在的离线 SDK 目录；该目标调用所选 Python 环境中的官方 W&B CLI，使用当前登录账号上传。打包和解包均不会触发上传。

## hope 集群

hope 提交机与计算作业共享 DolphinFS。代码包上传并解压到共享 release 目录，模型与数据保留在独立共享路径；每个作业写新的共享运行目录。本地与开发机之间人工上传代码、下载结果，开发机与计算节点之间直接读写共享路径。

参考配置为 [hope/mirroropd.hope](../hope/mirroropd.hope)，入口为 [scripts/hope-run.sh](../scripts/hope-run.sh)。提交前修改共享 checkout 路径、全部 `REPLACE` 路径和每个作业唯一的 `MIRROR_RUN_DIR`，再执行 `make hope-submit`。脚本需要 `MIRROR_MODEL_ROOT`、`MIRROR_DATA_ROOT`、`MIRROR_RUN_DIR`；可通过 `MIRROR_PYTHON`、`MIRROR_BACKEND`、`MIRROR_RECIPE`、`MIRROR_ALGORITHM`、`MIRROR_WANDB_MODE`、`MIRROR_GPU_IDS` 覆盖默认值，额外 CLI 参数直接传给 `run`。默认四卡、on-policy、数学配方和 W&B offline。

hope 作业内使用前台模式，使调度器观察 launcher 的退出码和终止信号；普通服务器长任务才用 `--detach`。队列提交成功只代表排队，训练完成仍需查看运行状态和审计。共享目录中的日志与结果由运行器统一落盘，不需要另起 SSH 同步进程。

参考镜像名标示 CUDA 12.8、PyTorch 2.8，而当前包要求 PyTorch 2.7。应在实际作业镜像内准备匹配的 Python 3.12、PyTorch 2.7.1+cu126、vLLM 0.10.0+cu126 和 FlashAttention 环境，并通过 `MIRROR_PYTHON` 选定解释器；不能直接照用镜像预装版本或把不同系统的虚拟环境目录当作可移植安装包。脚本在容器内检查导入及 PyTorch 主次版本后启动任务。模板沿用单 worker、4 张 80G GPU、32 vcore、128 GiB 内存和 128 GiB shared memory 的既有申请值，资源容量仍须真实短任务验证。仓库侧未执行 hope 提交或集群 GPU 验证。

## 失败处理与证据迁移

| 情况           | 排查与下一步                                                                            |
| -------------- | --------------------------------------------------------------------------------------- |
| 配置解析失败   | 按错误字段检查变量、JSON 类型、版本和跨字段约束，再用 `plan` 验证                       |
| 后端版本不符   | 对照当前包的 manifest 和 patch，保留原目录，在新目录重建                                |
| 输入核验失败   | 核对权重、tokenizer、模板、数据列、答案与预算；目录名和原安装清单不能代替字节校验       |
| 输出目录已存在 | 保留现场并换新目录；准备目录与训练目录也分开使用                                        |
| 训练失败或中断 | 查看 `state.json`、事件与已生成的 `backend.log`；核对本任务子进程和预约状态，再决定重跑 |
| 审计失败       | 根据缺样本、重复更新、非有限值或身份不一致的具体错误检查原始记录，不能只重写成功摘要    |

当前没有恢复完整 outer/inner、随机数、缓存与观测游标的续训协议。[编译器](../src/mirroropd/integrations/verl/compiler.py) 关闭自动 resume；配置 checkpoint 保存不能被解释为等价恢复。失败后的新尝试使用新目录，历史失败证据与新运行分别保存。

迁移机器时保留 `job.json`、`inputs.json`、`run.json`、`source/manifest.json`、运行源码、事件流、逐题结果和审计输出，并重新核验模型与数据的完整内容身份。相同 commit 与软件版本不能独自保证跨引擎、异步调度或 GPU 算子的逐 token 一致性。

scratch 位于运行记录登记的磁盘 cache，完整运行和 checkpoint 留在忽略目录；正式结论依赖的证据提取到 `data/`、`results/` 并绑定校验信息。新机器上的导入、容量与 GPU 执行需要实际验证，不能把历史环境库存当作迁移成功。
