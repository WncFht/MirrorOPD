# 运行与复现

本指南面向使用当前 0.2 接口的开发者。一次运行依次完成配置解析、后端与输入核验、源码冻结、资源预约、原生训练和完成审计。当前入口统一为 `mirroropd`；旧版实验的复现条件在各实验报告中单独说明。

## 环境与输入

使用 Python 3.12 的独立环境。已有 GPU 软件栈时，先核对兼容性再安装本包；数据转换、测试和数学判分依赖可用下面的命令安装：

```bash
python -m pip install -e '.[data,test,math]'
python -m mirroropd --version
```

[pyproject.toml](../pyproject.toml) 声明本包及 extras 的依赖范围，不是完整 CUDA 环境锁。GPU 运行还要求匹配的 PyTorch、vLLM、FlashAttention、Ray、TensorDict 和系统驱动。本机`environments/`可保存环境清单和 wheel 校验记录，该目录不随 Git checkout 交付。每次运行应保存实际依赖版本与来源；清单本身不能证明新机器上的 ABI、安装和 GPU 执行有效。维护工具的安装另见[开发维护指南](maintenance.md)。

内置 `deepseek-justrl` 模型 profile 要求显式 `model_root`，下面有学生 `DeepSeek-R1-Distill-Qwen-1.5B` 与教师 `JustRL-DeepSeek-1.5B` 的本地 Hugging Face artifact。模型须含 config、tokenizer 和权重，具有相同 token-to-ID 语义、特殊 token 与共享 chat template；目录同名不足以证明权重相同。没有合适的共同模板时，应显式配置 `models.chat_template`。

内置 `dapo-math` 数据 profile 从 `data_root/math/` 读取 DAPO 训练集及 MATH-500、AMC23、AIME25 验证集；具体路径以[模型 profile](../src/mirroropd/profiles/models/deepseek-justrl.json)和[数据 profile](../src/mirroropd/profiles/datasets/dapo-math.json)为准。可改用自己的 JSON profile 或已知字段覆盖。当前数据准备消费已有 parquet、JSONL 或 CSV，不提供自动下载入口。

验证集默认要求参考答案，训练集大小须覆盖一个完整 prompt batch。输入准备核对内容哈希、列映射、prompt 长度、词表和上下文预算。历史训练测试重叠、去重版本和解码协议的差异应在实验记录中保留；换数据不等于复现原有成绩。

## 配置解析

从仓库根执行，示例的 `/models` 与 `/data` 是占位路径。`plan` 不读取这些路径或检查 GPU：

```bash
mirroropd plan --recipe math-four-gpu --models deepseek-justrl --dataset dapo-math \
  --var model_root=/models --var data_root=/data --algorithm on_policy \
  --set logging.wandb.enabled=false --output runs/plan-on-policy.json
```

配方先组合模型和数据 profile，再展开显式变量、补齐默认值、应用 `--set`，最后校验 Job。缺失变量不从环境中推断。`--set` 的值先按 JSON 解析，未知路径、未知字段、类型不符或旧 schema 会被拒绝。

`--algorithm` 在 Job 解析后选择生产算法，选择 `on_policy` 时将 `training.inner_steps` 固定为 1；`mdpo`、`bpo` 沿用配方的 inner 设置。直接通过 `--set objective.algorithm=on_policy` 修改字段仍须满足 Job 的一次更新约束。完整默认值与展开结果以当前 `plan` 输出为准，不用旧 Hydra 字段覆盖新 Job。

`math-four-gpu` 配方默认开启 W&B；例子显式关闭云端记录，本地证据仍保留。需要 W&B 时在已配置的账号环境中启用，凭据不放入配方、Git 或日志。

## 后端准备与版本核验

```bash
make upstream
```

此命令通过包内 [backend.json](../src/mirroropd/integrations/verl/backend.json) 获取固定基线，并应用与当前包匹配的 [backend.patch](../src/mirroropd/integrations/verl/backend.patch)，默认输出到 `upstream/TA-OPD-v2`。也可以显式指定新的目录：

```bash
mirroropd backend --output upstream/my-pinned-backend
```

启动前核对实际 HEAD、完整补丁差异及后端运行源码中的未版本化文件。旧补丁或其他本地修改会被拒绝；出现冲突应保留原目录并换新目录重建，不覆盖正在执行的后端。更新到 0.2.1 后不能因目录名称相同就复用 0.2.0 的准备结果。

后端准备与安装 GPU 依赖是两件事。`make data` 只恢复 [data-manifest.json](../data-manifest.json) 登记的压缩研究证据，不下载模型或生成内置 profile 所需的全部训练输入。

## 不启动训练的准备检查

模型、数据和匹配的后端准备好后，将路径替换为实际位置，并使用一个尚不存在的输出目录：

```bash
mirroropd run --prepare-only \
  --recipe math-four-gpu --models deepseek-justrl --dataset dapo-math \
  --var model_root=/models --var data_root=/data --algorithm on_policy \
  --set training.outer_steps=2 --set evaluation.question_limit=4 \
  --set logging.wandb.enabled=false \
  --backend upstream/TA-OPD-v2 --output runs/my-prepare

mirroropd status runs/my-prepare
```

成功状态为 `prepared`。此时已有输入核验、规范化数据、冻结源码和 `backend.yaml`，尚未预约 GPU 或启动 Ray、FSDP、vLLM。`prepared` 不能证明模型推理、反向传播、显存容量、权重同步或训练完成，也不能对该目录要求完整训练审计。

`inputs.json` 记录实际模型、数据、词表和评测协议身份，`job.json` 保存准备后解析的绝对输入路径；实际运行配置可能因此与仅解析相对路径时的 `config_id` 不同。复现时比较运行中保存的身份，不只比较启动命令文本。

## 小规模训练与审计

GPU 软件栈和可预约设备满足要求后，使用另一个新目录运行小规模链路检查：

```bash
mirroropd run \
  --recipe math-four-gpu --models deepseek-justrl --dataset dapo-math \
  --var model_root=/models --var data_root=/data --algorithm on_policy \
  --set resources.gpu_ids='[0,1,2,3]' \
  --set training.outer_steps=2 --set evaluation.question_limit=4 \
  --set logging.wandb.enabled=false \
  --backend upstream/TA-OPD-v2 --output runs/my-canary

mirroropd status runs/my-canary
mirroropd audit runs/my-canary
```

`resources.gpu_ids` 明确物理设备身份，并须满足全局 batch、micro-batch 和 GPU 数的整除约束。检查可用资源时不得清理其他任务。单机 FSDP、SP=1、rollout TP=1 是当前验证范围；FileStore 的单进程推理组适配不能推广为多机或更大 executor group 的支持承诺。

两轮、四题检查仍沿用配方的生成长度和每题采样数，可能有明显 GPU 成本；它只检验小规模执行链路，不代表完整数据集成本或算法质量。正式实验应冻结代码、输入、评测和预算，按已完成 outer、实际更新次数与运行时间分别比较。

`status` 读取运行状态；若控制进程身份已失效，会把仍标为运行中的状态报告为 `orphaned`。`audit` 重新核对冻结源码、配置、退出状态、更新序列、rollout version 和逐题评测，并写 `verification.json`。只有完整审计通过才能计为完成，退出码 0 不足以替代审计。

`suite` 使用相同 Job 顺序执行所选算法，每组有独立子目录，失败即停止。它沿用配方各算法的实际更新预算；相同 outer 数不表示相同优化次数或耗时。

## 失败处理与证据迁移

| 情况           | 排查与下一步                                                                            |
| -------------- | --------------------------------------------------------------------------------------- |
| 配置解析失败   | 按错误字段检查变量、JSON 类型、版本和跨字段约束，再用 `plan` 验证                       |
| 后端版本不符   | 对照当前包的 manifest 和 patch，保留原目录，在新目录重建                                |
| 输入核验失败   | 核对权重、tokenizer、模板、数据列、答案与预算；目录名和原安装清单不能代替字节校验       |
| 输出目录已存在 | 保留现场并换新目录；准备目录与训练目录也分开使用                                        |
| 训练失败或中断 | 查看 `state.json`、事件与已生成的 `backend.log`；核对本任务子进程和预约状态，再决定重跑 |
| 审计失败       | 根据缺样本、重复更新、非有限值或身份不一致的具体错误检查原始记录，不能只重写成功摘要    |

当前没有恢复完整 outer/inner、随机数、缓存与观测游标的续训协议。[编译器](../src/mirroropd/integrations/verl/compiler.py) 关闭自动 resume；配置 checkpoint 保存不能被解释为等价恢复。失败后的新尝试使用新目录，历史失败证据与新运行分别保存。

迁移机器时保留 `job.json`、`inputs.json`、`run.json`、`source/manifest.json`、运行源码、事件流、逐题结果和审计输出，并重新核验模型与数据的完整内容身份。相同 commit 与软件版本不能独自保证跨引擎、异步调度或 GPU 算子的逐 token 一致性。

scratch 位于运行记录登记的磁盘 cache，完整运行和 checkpoint 留在忽略目录；正式结论依赖的证据提取到 `data/`、`results/` 并绑定校验信息。新机器上的导入、容量与 GPU 执行需要实际验证，不能把历史环境库存当作迁移成功。
